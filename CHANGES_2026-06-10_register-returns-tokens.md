# Изменение API: `POST /auth/confirm/register` теперь сразу возвращает токены

**Дата:** 2026-06-10
**Кому:** команда мобильного приложения (МП)
**Тип:** изменение контракта ответа (нестрогая обратная совместимость — см. ниже)

## Зачем

И регистрация, и вход подтверждаются по SMS-OTP. Раньше после успешной
регистрации (`/auth/confirm/register`) приложение должно было ещё раз пройти
вход (`/auth/login` → `/auth/confirm/login`), чтобы получить токены. Это
тратило **лишний OTP** (SMS/звонок) и добавляло лишний шаг.

Теперь подтверждение регистрации **создаёт пользователя и сразу выдаёт пару
токенов** — точно так же, как подтверждение входа. Отдельный вход после
регистрации больше не нужен.

## Что изменилось на сервере

| Эндпоинт | Было | Стало |
|---|---|---|
| `POST /auth/confirm/register` | `200 OK` с **пустым** телом | `200 OK` с телом `TokenResponse` (как у `/auth/confirm/login`) |

Все остальные эндпоинты, коды ошибок, статусы и rate-limit'ы — **без изменений**.

### Тело ответа `200` (новое)

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiI...",
  "accessExpiresIn": 900000,
  "refreshToken": "eyJhbGciOiJIUzI1NiI...",
  "refreshExpiresIn": 2592000000
}
```

- `accessExpiresIn` / `refreshExpiresIn` — время жизни токена в **миллисекундах**
  (access ≈ 15 мин, refresh ≈ 30 дней).
- Схема ответа **идентична** `/auth/confirm/login` и `/auth/master` —
  это та же модель `TokenResponse`.

### Коды ошибок (без изменений)

- `400` — неверный или истёкший код (`ErrorResponse` с машиночитаемым `code`).
- `429` — превышен лимит запросов.

## Что нужно сделать команде МП

1. **Новый флоу регистрации (целевой):**
   ```
   POST /auth/register          → 201 (OTP отправлен)
   POST /auth/confirm/register  → 200 + { accessToken, refreshToken, ... }
   ```
   Сохранить полученные токены и сразу считать пользователя авторизованным.
   **Убрать** последующий вызов `/auth/login` → `/auth/confirm/login` после регистрации.

2. **Парсинг ответа:** переиспользовать ту же модель/маппер, что и для
   `/auth/confirm/login` (`TokenResponse`). Отдельная DTO не нужна.

3. Старый клиент, который игнорирует тело `200`, **не сломается** на уровне
   транспорта (статус тот же), но останется на лишнем шаге входа — поэтому
   обновление желательно выкатить.

## Совместимость и порядок выката

- Сервер **обратно совместим**: статус ответа прежний (`200`), добавилось только
  тело. Старые версии приложения продолжат работать по старому флоу.
- Безопасный порядок: сначала деплой сервера, затем релиз приложения с новым флоу.
